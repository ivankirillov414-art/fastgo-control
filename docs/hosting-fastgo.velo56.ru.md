## Конкретное предложение

Текущий обычный хостинг «Профиспорта» оставить. В том же аккаунте 1Gb.ru добавить отдельный Linux VDS **HyperVPS «Комфорт», Москва: 4 CPU, 8 ГБ RAM, 120 ГБ NVMe, 1 IPv4, резервирование провайдера**. ОС Ubuntu 24.04 LTS. Панель PHP/MySQL не требуется.

Цена в официальном калькуляторе: **1 989 ₽ за месяц для физлица**, **2 183 ₽ за месяц для ИП/юрлица**, обычные ядра, без дополнительных услуг. При оплате за год опубликовано от 1 695 ₽/мес; годовую оплату для первого запуска не предлагаю. Окончательную сумму проверяем в аккаунте до оформления. Пробный период до 10 дней доступен по условиям провайдера, повторная доступность в существующем аккаунте не подтверждена.

Источник: https://api.1gb.ru/l_vds6.php — значения помесячной цены проверены также в коде официального переключателя периода, поскольку текстовый просмотр страницы показывает годовые цены.

Официальные рекомендации Supabase для самостоятельного размещения: минимум 2 CPU / 4 ГБ / 40 ГБ SSD, рекомендовано 4 CPU / 8 ГБ / 80 ГБ. https://supabase.com/docs/guides/self-hosting/docker

Новый домен покупать не требуется: используется согласованный поддомен **fastgo.velo56.ru**. Менять NS всего velo56.ru и переносить «Профиспорт» не требуется. После проверки сервера добавляется отдельная A-запись fastgo → IPv4 нового сервера. HTTPS — автоматический сертификат для поддомена.

Браузерное приложение, API/Edge Functions, Postgres, авторизация, приватные файлы, фоновые задания и настройки интеграций. Используем самостоятельный Supabase для сохранения API и бизнес-логики; простая загрузка HTML через FTP этого не переносит.

Текущий проект: oqgpjfikjpcplnxueoki. Аудит: база около 74 МБ; 140 таблиц в расширенном экспорте, 140 исходных файлов в приватных бакетах. До исправления резерв охватывал только workshop_* и один бакет; поэтому старые копии нельзя считать полными копиями всех разделов FastGo.

## Порядок переноса и граница готовности

1. Новый сервер поднимается из зафиксированной версии официального Docker Compose. Внутренние Postgres, Studio и служебные сервисы наружу не открываем. Секреты хранятся вне Git/веб-каталога; SSH по проверенному ключу. Интернету доступны HTTPS и необходимый SSH.
2. До переключения получаем согласованный экспорт схемы/данных Postgres и Auth; отдельно переносим фактические bytes Storage, функции, разрешения/RLS, расширения, расписания, настройки SMTP/интеграций. JSON-архив восстановления не выдаём за готовый перенос Postgres.
3. На закрытой копии проверяем восстановление базы и файлов, права, вход, чтение реального заказа без изменения, изолированный рабочий цикл и резервное восстановление. Уведомления, списания, платежи и webhook-повторы в копии отключены.
4. Сначала готовим приложения к новому адресу, учитываем офлайн-очереди и старые клиенты. JWT/refresh-сессии не обещаем сохранить без проверки совместимости ключей Auth: может потребоваться повторный вход.
5. В согласованное короткое окно ограничиваем запись в старую базу, дожидаемся очередей, снимаем финальный согласованный экспорт и сверяем количество/хеши данных и файлов. Лишь после этого переключаем адрес. Никогда не допускаем две независимо записывающие основные базы.
6. Сохраняем исходный сервер и проверенный возврат. После первой записи в новую базу простой возврат DNS запрещён: сначала переносим новые операции обратно. Старую базу не удаляем при первом успешном запуске.

Сейчас **перенос не выполнен**: нового VPS и SSH-доступа ещё нет. Не выполнены серверная установка, полноценная репетиция Postgres restore, переключение и проверка fastgo.velo56.ru. Отдельный сервер — необходимая покупка для выбранного полного переноса; обычный FTP-доступ этого ограничения не снимает.

## Резервирование независимо от переноса

Серверные архивы зашифрованы; семь успешно завершённых суточных дат в Asia/Yekaterinburg. Старейший день удаляется только после записи и проверки нового, не по безусловному возрасту файла. Пока не накоплено семь новых полных суточных копий, прежние архивы сохраняются.

Windows, телефон и ТСД сохраняют копии в приватных каталогах, проверяют размер/хеш и догружают доступную историю после офлайна. Выключенное устройство не может физически получить копию в этот день. Локальная несинхронизированная очередь резервируется отдельно. Ключ восстановления владельца сохраняется защищённо; копия зашифрованных файлов у сотрудника не равна доступу к расшифрованной базе.

После переноса VPS дополнительно должен иметь ежедневный согласованный Postgres dump и зашифрованный файловый резерв с той же безопасной ротацией. Снимок диска провайдера дополняет их, но не заменяет проверку восстановления приложения.
