# Архитектура, безопасность и приёмка
Статус: требования к будущей реализации. Реализован только protocol.mjs.

## Данные и доверие
Сервер читает актуальную роль из БД: seller/owner/developer. Цены, наличие и фискальное сопоставление берутся из серверного каталога. Клиентские поля цены игнорируются. Авторизация терминала ограничивается его очередью и организацией; одноразовый код привязки имеет короткий срок, ограничение попыток, хранится в виде хэша, погашается атомарно. После удаления приложения доступ отзывается. Не передавать service_role/админ-ключи на терминал или в браузер.

HTTPS; секреты в закрытом хранилище; ротация и отзыв. Облачные вебхуки проверяются по документированному механизму Эвотора с различием пользовательского и прикладного токенов. Защита от повторов: идентификатор события, хэш содержимого, уникальные receipt_id и checkout_id. Хэш протокола не доказывает происхождение события.

Резервирование и проведение продаж одной транзакцией в общей системе блокировок склада. Устаревшая цена/изменённый чек — ручная сверка без автоматической записи успеха. При незавершённом задании закрытие учётной смены запрещено; фискальная смена Эвотора и учётная смена FastGo сопоставляются явно.

На кассе: сохранять принятую команду до вызова SDK; пустую/чужую корзину проверять перед открытием; после сбоя сначала искать существующий чек. Не открывать повторно при unknown. Событие completed необходимо сопоставить с фактически сформированным документом и его оплатами; событие opened недостаточно. Не печатать автоматически фиктивные чеки для тестов.

Логи: события без секретов, контактов клиентов и полных чеков; идентификатор операции, статус, код ошибки, время. Сроки хранения определяет политика оператора. Для служебного доступа журналировать действия, выдавать минимальные права. Резервные копии и восстановление проверять на синтетических данных.

## План испытаний
| Сценарий | Ожидаемый результат | Уровень |
|---|---|---|
| Подмена цены клиентом | Серверная цена | Unit: пройден |
| Нет фискального сопоставления | Блокирование | Unit: пройден |
| Нет остатка/повтор позиции | Блокирование | Unit: пройден |
| Повтор payload | Стабильный хэш | Unit: пройден; идемпотентность БД ещё нужна |
| Смешанная оплата | Точная сумма | Unit: пройден |
| Подмена чека/терминала | Отказ сверки | Unit: пройден |
| Unknown | Нет автоматического повтора | Unit: пройден |
| Чек уже проведён | Нет повторной фискализации переходом | Unit: пройден; БД ещё нужна |
| Два кассира покупают последний товар | Одна успешная резервация | БД: не выполнен |
| Чужой открытый чек | Не очищается | Терминал: не выполнен |
| Потеря связи после оплаты | Восстановление одного результата | E2E: не выполнен |
| Перезапуск адаптера | Сохранение незавершённой команды | Терминал: не выполнен |
| Отзыв устройства | Доступ запрещён | API: не выполнен |
| Повтор webhook | Одна запись продажи | API/БД: не выполнен |
| Закрытие смены с активной командой | Запрет | БД: не выполнен |
| Возврат | Один чек возврата и одно восстановление остатка | E2E: не выполнен |

Протокол приёмки: версия APK + SHA256, версия сервера, SDK/зависимости, модель, POS/ОС/ФФД, тестовый режим, сценарий, ожидаемый/фактический результат, обезличенное доказательство, исполнитель, дата. Не считать unit-тесты подтверждением фискальной совместимости.

## Требования к выпуску кода
Зафиксированные зависимости и лицензии, отсутствие секретов, комментарии к границам доверия и денежным расчётам, воспроизводимая сборка, release notes, подпись APK, журнал дефектов, инструкция удаления/отзыва и восстановления. Перечень SDK-разрешений составить по реально используемым API, не запрашивать широкие права заранее.
